Section I: Executive Summary

1. Problem Statement

Vaani today answers with generic language because it lacks grounded, per-product, per-user, per-region signal. Every DECIDE-turn (“achha hai?”, “kitne ka hai?”, “kab aayega?”) gets the same shape of response regardless of the product’s return rate, the user’s size history, the pincode’s delivery ETA, or the seller’s trust profile.

This KRD ships the data foundation that grounds every Vaani response. It defines: (a) the 29 fields (19 P0 + 10 P1) that must be available to the response layer on every turn, (b) the source tables, c) the pre-computed views and their grain, (d) refresh cadences, (e) the hot-store hydration contract that the Vaani orchestrator will pull from, and (f) data-layer enforcement of silent-when rules so that thin/low-confidence signals never reach the LLM.

2. Product Thinking

The instrumented Vaani we shipped told us conversational shopping is buildable. V1 must show it is worth grounding. Four claims we want the launch to support or reject:

  • Data-grounded answers convert better than generic ones. A response that names the return rate, seller trust, and delivery ETA earns more session → cart than a generic “yeh accha hai.”

  • Return-reason + variant-return is a decision-material steer. Users given a size warning based on variant return rate returning less and adding-to-cart more.

  • User personalization compounds. Users addressed with their inferred size, budget band, and past-order references show higher repeat-engagement rates than the baseline.

3. NSM — Success & Check Metrics

3.1 Primary Success Metric*

*

MetricDefinition
Enriched-turn → cart-add rate % Vaani turns on PDP (DECIDE turns) that result in an add-to-cart within the same session, for Treatment (enriched payload) vs Holdout (baseline payload).

3.2 Secondary Metrics*

*

MetricDefinition
Per-field surface rate % turns where each P0/P1 field appears in the response (only among turns where the field was non-null and eligible). Diagnoses under-use.
Fresh-search rate on pivot % turns with pivot_signal=true where the new query does not carry forward the previous product’s attributes (verifies data isolation, feeds context-lock fix).
Alternate-product CTR (G1) % turns where Vaani offered an alternate and the user clicked into it.
Size-recommendation acceptance % turns where Vaani pre-recommended a size (D2) and the user selected the same size.
Return-window action success % RETURN_HELP turns that end in a submitted return request within the session.

3.3 Guardrail Metrics*

*

MetricDefinition
Response latency (P95) End-to-end turn latency with enriched payload vs baseline. Target: no more than +200ms over baseline.

2. Scope

2.1 In Scope

  • 29 fields (19 P0 + 10 P1) — see 3.1. Every field has: source, pre-computed view, silent-when rule, refresh cadence, and framing library (framings in the context note, not restated here).

  • Pre-computed views — a set of ~15 hot-store tables covering product, seller, user, geo, order, alternate, and cohort aggregates. Detailed schemas in 4.

  • Orchestrator hydration payload contract — a single wire format the Vaani orchestrator receives on every turn, with defined nullability and field types. 4.5.

  • Data-layer silent-when enforcement — every view returns null when sample size / staleness / thin-cohort thresholds are violated. LLM sees null; LLM does not decide silent-when. 4.6.

  • Refresh cadence tiers — real-time (variants, inventory, in-transit orders, ETA, price ladder, sale calendar), near-real-time (return-window orders), daily-batch (all aggregates, cohort summaries, personalization stats, alternates ranking, price trend). 4.7.

  • Cohort key definition — canonical (region_bucket, budget_band, sscat_history_overlap) tuple used by B4 (cohort review) and G1 (cohort-anchored alternate). 4.8.

  • Metric instrumentation — logging on payload hydration, field-surface rate, silent-when compliance, per-view hit/miss. 7.

  • A/B experiment plumbing — Treatment (enriched payload) vs Holdout (baseline). 5.

2.2 Out of Scope

  • Prompt / intent changes — shipped in a separate KRD.

  • P2 fields — H1 (in-session product-view stack), H2 (cross-session memory) Deferred to next cycle.

  • Fully-generative context selection — the LLM picks which fields to use per prompt; the data layer does not pre-select on its behalf beyond silent-when.

  • New UX surfaces — the ORDER_TRACKING screen entry-point design ships elsewhere.

3.2 Silent-When Enforcement Contract

Silent-when rules are enforced at the data layer, not the LLM.

  • Every view materializes rows only when the sample / threshold conditions are met.

  • The orchestrator’s payload will contain null (or [] for list fields) for any field whose silent-when trigger fires.

  • The LLM’s rule is simple: if a field is null, do not surface it, do not reason about it, do not mention it is missing (unless the user explicitly asked for it).

  • This makes the LLM prompt simpler AND makes safety a data-contract guarantee, not a prompt-adherence hope.

4.5 Orchestrator Hydration Payload

The Vaani orchestrator receives one payload per turn. The wire format is fixed; nullability is per 3.1 silent-when rules.

Trigger: every turn where Vaani is invoked, keyed by (user_id, product_id?, pincode, current_screen, intent).

Hydration: the orchestrator does an in-parallel fanout to hot store keys and composes the payload.

**

**Sanitization rules the orchestrator MUST enforce:

  1. user.returner_tier is exposed. user.return_history_raw (V-D5 numeric fields) is stripped.

  2. Any field where silent_when_triggered = true per its view definition → replaced with null.

  3. Views that fail to hydrate within 200ms → return null for that field; log to meta.views_failed.

  4. V-F3 past orders are NOT hydrated on every turn. They are fetched via a lazy tool call invoked by the response layer when the intent is ORDER_TRACKING or RETURN_HELP, or when the LLM signals the need. This keeps the steady-state payload small.

*

*4.6 Data Quality & Silent-When Enforcement (recap)

  1. Silent-when is enforced at the view level and re-enforced at the orchestrator level. LLM never applies silent-when.

    1. At view level: sample-size and threshold rules result in null-populated rows (or omission), per the per-field spec in 3.1.

    2. At orchestrator level: a defensive re-check runs before the payload is emitted. If a view returns non-null but sample_size below threshold (e.g., a stale row from before threshold enforcement was tightened), the orchestrator over-writes with null and logs.
