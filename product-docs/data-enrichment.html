KRD — Vaani Data Enrichment

Grounding Vaani in per-product, per-seller and per-user data — the processor layer that fetches it and the contract that delivers it to the LLM.

Current Status Draft for engineering handoff

Section I: Summary

1. Problem Statement

Vaani answers with generic language because it lacks grounded, per-product, per-seller, per-user signal. Every DECIDE turn — "achha hai?", "kitne ka hai?", "kab aayega?" — gets the same shape of response regardless of the product's return rate, the seller's trust profile, the delivery ETA to that pincode, or what the user has bought before.

This KRD ships the layer that fixes that. It defines:

  • Processors — the named units that fetch enrichment data, one per downstream API, requested per turn by the intent layer.
  • The output contract — how a processor converts downstream JSON into a token block the response layer can use directly, with no arithmetic or interpretation left to the LLM.
  • The build sequence — what ships in V1, what follows in P0 and P1, and what is held in backlog.
  • The data layer — source tables, pre-computed views, refresh cadence, and data-layer enforcement of suppression rules so that thin or low-confidence signals never reach the LLM.

2. Success Metrics

Type Metric Definition
Primary Enriched-turn → cart-add rate % of Vaani DECIDE turns on PDP resulting in an add-to-cart in the same session, Treatment (enriched) vs Holdout (baseline).
Secondary Per-key surface rate % of turns where each emitted key appears in the response, among turns where the key was present in the block. Diagnoses under-use.

Section II: Requirements

1. Scope

1.1 In Scope

  • Processor framework — contract, selection, parallel execution, failure handling, output normalization.
  • Eight processors across four build phases, each with a declared field set, suppression rules and emitted block.
  • Pre-computed views backing the processors that need aggregation, with schemas, grain and refresh cadence.
  • Data-layer suppression — every view and processor returns nothing for a key whose sample-size or staleness threshold is not met.
  • Frontend contract — supplier_id passed on every PDP-context invocation.
  • Instrumentation — per-processor hit, miss, timeout and suppression logging.
  • A/B plumbing — Treatment (enriched) vs Holdout (baseline).

1.2 Out of Scope

  • Prompt and intent changes — shipped in the Vaani V1 Prompt Spec.
  • Backlog fields (§3.4) — specified here for sequencing, not built in this cycle.
  • New UX surfaces.

2. Processor Architecture

2.1 What a Processor Is

A processor is a named, LLM-addressable unit of information. The intent layer decides which processors a turn needs; the orchestrator runs them in parallel; each converts one downstream API's response into a compact token block that the response layer reads directly.

Four invariants hold for every processor:

  1. One processor, one downstream API. A processor never fans out to two systems. If information needs two calls, it is two processors.
  2. Suppression happens in the processor. Threshold rules are enforced in code before emit. The LLM never receives a value it is not allowed to use.
  3. A processor is never on the critical path. Timeout or error means the block is omitted and the turn continues. A missing block degrades the answer; it never fails it.
  4. Processors are named for meaning, not for endpoints. The LLM addresses what the information is; the service behind it can move.

2.2 Turn Flow

Layer 1 — Intent Classifier
  emits { intent, requires_screenshot, pivot_signal, processors[] }
        │
        ▼

        │
        ▼  parallel fanout, 200ms budget, one downstream call each
  ┌───────────┬───────────────┬──────────────┬─────────┐

  storefront  return_recon    order aggregate
  └───────────┴───────────────┴──────────────┴─────────┘
        │  failed or timed-out processors drop out here
        ▼
Normalizer
  suppression → omit key · precompute framings · resolve dates
  cap lists · strip internal fields · JSON → one flat block per processor
        │
        ▼

  constitution + per-intent prompt + token blocks + screenshot if flagged

2.3 Processor Contract

Every processor declares exactly these eight things. A processor with a blank in this table is not ready to build.

Declaration Meaning
name <entity>_<facet>, snake_case. Entity is one of product, seller, user, context. The name is what the intent layer emits and what the token block is named after, so it is a public interface.
keys required e.g. product_id + seller_id. If a key is unavailable on the turn, the processor is not invocable and the orchestrator drops it silently.
downstream API Exactly one, named service and endpoint.
freshness RT / NRT / BATCH. Determines whether a stale read is acceptable and how long a result may be cached within a session.
latency budget In ms. On breach the block is omitted and logged to meta.processors_failed. Budgets must sum within the +200ms P95 guardrail under parallel execution.
emitted block Block name and exhaustive key list, with units and formatting. This is the contract the response prompts are written against.
suppression rules Per-key thresholds, enforced in the processor.
eligible intents Which intents may request it, and which receive it by default.

2.4 Processor Selection

The intent layer's output gains one field:

{
  "intent": "PRODUCT_INQUIRY",
  "requires_screenshot": false,
  "pivot_signal": false,
  "processors": ["product_post_order_info"]
}

The request is advisory. The orchestrator resolves the set that actually runs:

final = default_map[intent] ∪ (llm_requested ∩ allowlist[intent])

The default map is a deterministic floor; the allowlist is a ceiling. The floor guarantees that a turn always receives the processors its intent requires regardless of classifier behaviour. The ceiling prevents an unrecognised processor name or an unnecessary fetch.

Intent Default May additionally be requested
PRODUCT_INQUIRY product_info product_post_order_info, seller_info, user_profile, user_past_10_orders
VARIANT_SELECT product_info product_post_order_info
REASSURANCE product_post_order_info seller_info, seller_return_reason
BUY_HELP, CHECKOUT_HELP product_info —
ORDER_TRACKING user_order_transit user_past_10_orders
RETURN_HELP user_order_in_return_window user_past_10_orders
SEARCH, REFINE, INFO none —
GREETING, OUT_OF_SCOPE, UNCLEAR none —

2.5 Output Contract

Downstream APIs return nested JSON built for services. The normalizer converts each response into one flat block the response layer can speak from without transformation.

Grammar. One block per processor. Block name is the processor name, uppercased. Pipe-delimited key=value, emitted as a single line.

PRODUCT_POST_ORDER_INFO: |return_rate_m3=12% (category 22%, better)|delivered_m3=1284|top_return_reason=size (58% of returns)|quality_returns=4%

Normalization rules.

Rule Detail
Omit, do not null A suppressed key is absent from the block entirely. A key that is not present cannot be surfaced, hedged about, or reported as missing.
Empty is not silence For list processors, emit orders=none when the list is genuinely empty. Absent means stay quiet; none is an established fact the response layer may state.
Precompute every framing return_rate=12% (category 22%, better) — not two raw numbers. Any comparison or arithmetic left to the LLM is a correctness risk.
Pre-resolve dates eta=Sat 18 Jul (4 din) — never an ISO timestamp. Date arithmetic is performed in the processor.
Round and humanize numbers Percentages to whole numbers, currency to integer INR, counts in plain digits. No floats.
Cap every list Variants ≤ 8, past orders ≤ 10, review themes ≤ 3. Caps are configuration, never part of the processor name.
One level of nesting maximum {k:v,k:v} and [a,b,c] are permitted. Deeper structures flatten to dotted or compound keys.
No raw identifiers Product, variant, order and seller IDs are omitted unless an action the assistant can take requires one.
Per-processor size budget Enforced at emit, in characters. Every block rides in the Layer 2 system prompt.

Failure handling. A processor that errors or exceeds its budget emits no block. Its name is logged to meta.processors_failed. The response layer's standing rule covers the rest: answer from what is present, and do not refer to what is absent.

4.4 Suppression Enforcement

Suppression is enforced at two levels and never by the LLM.

  1. View level. Sample-size and staleness rules null the column, per the per-field rules in §3.
  2. Processor level. A defensive re-check runs before emit. A non-null value whose sample size sits below threshold is dropped and logged.

The processor omits the key entirely rather than emitting a null. The response layer's rule is therefore a single line: answer from the keys present.

4.5 Frontend Contract

To key seller-grain data, Android must pass supplier_id alongside product_id on every Vaani invocation in a product context.

  • Sent whenever Vaani is opened or invoked from a PDP.
  • Updated when the user switches to another product.
  • Where unavailable, the agreed null state is passed. No value is inferred on the client.
  • product_info resolves its seller from this identifier rather than selecting the first supplier, so every processor on a turn resolves the same seller.

Frontend does not fetch enrichment data, apply eligibility logic, or render new UI.
