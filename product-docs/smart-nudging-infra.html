1. Background and problem context

Vaani currently supports page-level and repeated-visit nudges across surfaces such as MAIN, CATALOG_SEARCH_RESULTS, CATALOG_LISTING_PAGE, SINGLE_PRODUCT, CART, and PAYMENT_SELECTION. Existing active rules are mostly based on page_intro and repeated_page_visit_without_engagement, with per-rule controls such as lifetime_max, session_max, delay_ms, cooldown_seconds, and visit_threshold.

The current system has per-nudge sunset logic and same-type cooldowns, but lacks holistic session-level and lifetime-level orchestration. As more nudge types are added, the system needs global controls to prevent over-nudging, sequence nudges deliberately, and adapt to user responsiveness.

Also the next major capability is zero-click nudging. The goal is to identify when a user is browsing the app, has seen enough products, has not clicked any product, and is likely to drop off. Just before that likely drop-off, Vaani should deliver a context-rich nudge based on current session behavior, previous session behavior, previous intent, search usage, order maturity, and Vaani usage.

2. Objective and non-goals

The objective is to build a configurable nudge infrastructure that supports existing nudges, adds global anti-spam controls, enables product-exposure-based zero-click triggers, and allows backend-generated personalized content.

  • Objective 1: Continue supporting existing page_intro and repeated_page_visit_without_engagement rules.

  • Objective 2: Add global controls across all nudge types, not only within a rule or type.

  • Objective 3: Add zero_click_product_exposure as a reusable trigger family.

  • Objective 4: Enable context-rich rules based on previous session, category/SSCAT intent, search behavior, app-open gap, OD stage, and Vaani usage.

  • Objective 5: Pass enough context to backend content generation so nudges feel personalized, helpful, and non-generic.

Non-goals for MVP: a fully learned drop-off prediction model, free-form LLM copy without templates/guardrails. These can come later once deterministic counters and governance are stable.

3. Product principles

PrincipleRequirement
Helpful, not interruptive Nudges should be delayed until the user has demonstrated enough browsing/no-click behavior.
Context first Prefer a specific nudge such as resume previous category or refine search over a generic help prompt.
Configurable by Product New hypotheses should be expressible through rule config rather than hard-coded logic.
Governed globally Session and lifetime exposure must be controlled across all nudge types.
Safe fallback If personalization context is missing or weak, use a generic template or suppress the nudge.
Measurable Every shown and suppressed nudge must be logged with reason codes and outcome events.

6. New zero-click trigger family

Add a new trigger type called zero_click_product_exposure. This trigger fires when the user has seen enough valid product impressions but has not clicked any product or created meaningful product engagement.

Zero-click eligible =
valid_product_views >= configured threshold
AND product_click_count == 0
AND optional product_engagement_count == 0
AND governance controls allow nudge

6.1 Valid product view definition

Tech should implement a standardized definition of a valid product view so that repeated or accidental impressions do not trigger nudges incorrectly.

  • Product cards are at least 50% visible on screen.

  • Visibility duration is greater than or equal to configured threshold, e.g. 500 ms or 1000 ms.

  • Product is not a duplicate impression already counted within the configured dedupe scope.

  • Impression is attached to a valid surface, feed request, and session.

{  
  "valid_impression_definition": {  
    "min_visible_percent": 50,  
    "min_visible_duration_ms": 750,  
    "dedupe_scope": "session_surface_visit"  
  }  
}

7. No-click hypotheses and nudge logic

The system should support the following no-click hypotheses through reusable triggers and conditions. These are not separate hard-coded trigger types; they should be expressed through the same schema.

IDHypothesisRule patternContent intent
H1 Overall session zero-click session_product_views >= x AND session_product_clicks == 0 generic_discovery_help
H2 Surface-specific zero-click current_surface_product_views >= x AND current_surface_product_clicks == 0 homepage_discovery_help / category_filter_help / search_refinement_help
H3 Latest feed visit zero-click current_surface_visit_product_views >= x AND no click in latest visit surface-specific help
H4 Aggregate feed zero-click surface_session_aggregate_product_views >= x AND no surface clicks surface-specific help
H5 Short reopen after previous no-click short app-open gap AND previous_session_had_no_product_click AND current zero-click AND previous_session_views >=y short_reopen_unresolved_mission
H6 Previous strong intent, current no-click previous_intent_strength_score >= threshold AND current zero-click resume_previous_category_intent
H7 Same SSCAT overexposure dominant_sscat_view_share >= p AND no click same_sscat_refinement_help
H8 Previous-intent SSCAT shown again, still no click current_previous_sscat_view_share >= p AND no click resume/refine previous SSCAT
H9 Previous intent mismatch previous_intent exists AND current_previous_sscat_view_share <= p resume previous category
H10 Long-gap exploration user app_open_gap_bucket in long-gap buckets AND high threshold zero-click soft_exploration_help
H11 Search-capable user zero-click has_text_search_current_session AND search_results_product_views >= x AND no click search_refinement_help
H12 Vaani already used in session vaani_used_current_session == true suppress generic zero-click
H13 Nudge fatigue / repeated ignore ignored_nudges_count >= max_consecutive_ignored suppress or pause nudges

11. Priority, conflict resolution, and suppression

Multiple nudges may become eligible at the same time. The engine should never fire all of them. It should select one rule based on global controls, rule eligibility, and priority.

  1. Check whether global nudging is enabled.

  2. Apply global suppressions: first_nudge_delay_seconds, cooldown_between_nudges_seconds, max_nudges_per_session, max_lifetime_nudges, max_consecutive_ignored.

  3. Evaluate all rules for the current surface and GLOBAL rules.

  4. Remove rules failing trigger, condition, sunset, or cooldown checks.

  5. Select one rule using the priority policy.

  6. Generate content using a backend content generator.

  7. Fire the nudge action.

  8. Log nudge shown and update counters.

Priority bandNudge type
120-150 Previous strong intent / near-order resume
100-119 Short reopen after unresolved mission
80-99 Search refinement zero-click
70-79 Surface-specific zero-click
60-69 Generic session zero-click
40-59 Long-gap exploration
10-39 Basic page intro / education nudges

If a rule becomes eligible during a global cooldown window, it should be skipped and not queued. Normal trigger evaluation should run again later.

12. Backend personalized content generation

The backend content generator should receive a structured context payload every time a rule is selected. The goal is to produce a nudge that feels context-aware, personalized, short, helpful, surface-relevant, safe to say aloud, and non-spammy.

Nudge Engine selects rule
-> builds content context payload
-> Content Backend chooses content intent
-> Content Backend fills template or generates controlled text
-> Safety/length/language checks
-> Voice Assistant speaks final nudge

At minimum, the payload should contain request_metadata, selected_rule, governance_state, current_session_context, current_surface_context, current_product_exposure_context, previous_session_context, intent_memory_context, user_profile_context, search_context, vaani_context, cart_checkout_context, content_constraints, and fallback_context.

17. Acceptance criteria

Infra acceptance criteria:

  1. Tech can configure a zero-click nudge based on total session product views and no product click.

  2. Tech can configure zero-click separately for homepage, search results, and CLP.

  3. Tech can configure latest feed visit versus aggregate feed visits in a session.

  4. Tech can configure rules using previous-session no-click behavior.

  5. Tech can configure rules using previous strong intent, including cart, wishlist, buy-now, payment, or high SSCAT engagement.

  6. Tech can configure rules using current-vs-previous SSCAT overlap.

  7. Tech can suppress nudges if Vaani has already been used in the current session.

  8. Tech can suppress nudges based on global cooldown, max session nudges, max lifetime nudges, and ignored nudges.

  9. Tech can enforce first-nudge delay after session start.

  10. Tech can log shown, skipped, suppressed, and outcome events with reason codes.

Content acceptance criteria:

  1. Backend receives a structured context payload for every selected nudge.

  2. Backend can generate or template content based on content_intent.

  3. Backend falls back to generic content if required context fields are missing.

  4. Content is short enough for voice playback.

Appendix C. Glossary

TermMeaning
Zero-click user A user who has viewed enough products but has not clicked any product in the configured scope.
Valid product view A product card impression that meets visibility, duration, and dedupe requirements.
Surface The app screen or context where the user is currently browsing, such as MAIN, CLP, search results, PDP, cart, or payment.
Feed visit One continuous visit to a feed/surface, distinguished by feed_visit_id.
Session aggregate Cumulative activity across multiple visits to the same surface in the same session.
Previous intent A compact summary of strong user interest from a prior session or earlier in the same session.
SSCAT Sub-sub-category or narrow category used to represent product-category intent.
Content intent The backend content-generation objective selected by rule, such as search_refinement_help or resume_previous_category_intent.
Governance Global controls that prevent over-nudging across all rule types.
Ignored nudge A nudge after which the user does not initiate Vaani within the configured window, typically 60 seconds.
