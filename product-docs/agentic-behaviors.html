Vaani — Agentic Behaviors Product Note

Owner: Ishan Sharma Status: Draft for alignment (pre-KRD) Companion doc: Vaani — Context Enrichment Product Note (data fields). Scope: New agentic behaviors Vaani should perform (not just describe). Applies primarily to PDP and search/CRP surfaces, with one order-state action.

1. Purpose

This note answers what does Vaani do. Every behavior below is agentic – Vaani takes an action on the surface (image search, filter apply, variant swap, size pre-select, return initiation) and narrates it, rather than instructing the user to do it themselves.

Each behavior is specified with the same discipline as fields in the context note: trigger, action, consumption shapes (what Vaani says), silent-when, 0-result handling, guardrails.

2. Prioritization

Priority reflects both user value and build dependency (a behavior that another P0 behavior depends on is itself P0).

  • P0 — Anchor set. Must ship together, in this order.

  • B0 - Resume past intent from HP

  • B1 — PDP → anchored constrained search

  • B2a — Search page → agentic filter application

  • B2b — Filter-importance intel (data + surfacing)

  • B4 — Variant swap in-place on PDP (prerequisite of B1 precedence rule)

  • B7 — Progressive relaxation on 0 results (fallback that B1 / B2a / B3 rely on)

  • P1 — High-leverage follow-ups. Ship after P0 lands.

  • B3 — Sort-order steering

  • B5 — Size auto-select on PDP

  • P2 — Depth adds. Ship once the anchor set is stable.

  • B6 — Exclusion filters via chat

  • B8 — Return-window agentic action

  • Later

    • Side-by-side disambiguator using UI!

Rationale for the P0 grouping: B1 and B2a are the two headline agentic capabilities. B2b is the intelligence that lets both B1 relaxation and B2a proactive nudges work well. B4 must exist before B1 launches because otherwise B1 will misfire on any "blue mein dikhao" utterance that a variant swap could have handled cleanly. B7 must exist because all filter/search-changing behaviors will occasionally return 0 results and cannot dead-end.

3. Behaviors

B1 — PDP → anchored constrained search [P0]

Trigger. User is on PDP. Utterance combines an anchor phrase ("aisa hi", "similar", "isi tarah ka", "iske jaisa") with a constraint on colour, price, length, fabric, pattern, sleeve, neckline, etc.

Precedence rule. Before firing B1, check whether the constraint is satisfiable by a variant of the current product (via B4). If yes, do B4 (in-place swap) not B1 (new search). Only escalate to image-search when no variant satisfies.

Action. Trigger image/style search seeded on the current product, apply the parsed constraint as a filter on the result set, and open a fresh feed with a "back to original" pill.

Data dependencies.

  • Image-search index (visual similarity by product image).

  • Utterance → filter lexicon (deterministic parse table, PM-authored).

  • Filter-importance intel (B2b) for relaxation ordering.

  • Product variants (Context note C3) to enforce precedence rule.

Consumption shapes.

  • Announce-and-open: "Blue mein ₹500 se kam wale nikale — 24 options dikha rahi hoon."

  • Silent apply when utterance is unambiguous and single-constraint.

  • Clarifier when the constraint is ambiguous: "Blue matlab navy chahiye ya sky?"

  • Filter-summary phrasing when >1 constraint: "Blue + cotton + ₹500 tak — 12 options."

  • Empty-set handoff to B7: "Blue mein ₹400 tak nahi hai — ₹450 tak dikhaun?"

Silent-when.

  • Utterance is about the current product itself (opinion / colour-check on this PDP), not a "similar" request.

  • Constraint is satisfiable by variant (defer to B4).

Guardrails.

  • Cap results to top 12 in the new feed.

  • Preserve one-tap return to original PDP.

  • Do not invoke image-search for a pure colour change without other constraint — that's B4.

  • Do not chain more than one image-search per turn.

B2a — Search page → agentic filter application [P0]

Trigger. User is on a search/CRP page. Utterance names a constraint attribute ("blue mein", "under 500", "cotton", "L size", "Reliance Trends jaisa nahi") or a modifier ("thoda sasta", "aur lamba").

Action. Parse utterance → filter(s), apply on the current feed, refresh the visible list, narrate what changed.

Consumption shapes.

  • Confirm-on-apply: "Blue + under ₹500 laga diya, 45 options bache."

  • Silent apply if user is mid-flow and count change is small.

  • Undo: "wapas hata do" → last filter removed, narrated.

  • Reset: "sab hata do" → all Vaani-applied filters cleared.

  • Stack: additional filters within the same turn stack additively.

  • Toggling: naming an already-applied filter attribute with a new value replaces it, not stacks.

Silent-when.

  • Utterance is a description, not a constraint ("achha lag raha hai").

  • Filter would produce zero change (already applied).

Guardrails.

  • Max 5 Vaani-applied filters visible in the pill row; pruning oldest if overflow.

  • Deterministic parse — never LLM-fabricate a filter that isn't in the taxonomy.

  • Confirm on high-blast-radius filter (e.g., sscat change): "sscat badal ke saree dikhaun?"

  • 0-result → hand to B7.

B2b — Filter-importance intel [P0]

Not a user-visible behavior — a data + surfacing capability that powers B1 relaxation, B2a proactive asks, B3 sort steering, and B7 relaxation ordering.

Data. Per (sscat, current-filter-state, user-profile) a ranked list of candidate next-filters, each with:

  • Impact on result-set size (how much it narrows).

  • Impact on click / order rate (how much it improves buyability).

  • Whether user has an inferred preference for this filter (from Context D1 / D4 / D5).

  • Filter interdependencies (e.g., length + fit interact).

Recommend an offline pre-computed table per (sscat, top-K filter states) refreshed weekly, plus a lightweight real-time overlay for result-count. Do not compute rank at request time.

Consumption shapes (how Vaani uses this data in dialogue).

  • Reactive elicit (after user lands broad): "200 kurte hain — length aur fabric bata do, top 20 dikhata hoon."

  • Proactive nudge on landing: if result count > threshold AND top-ranked filter is unset AND user has no preference → "Length important hai — knee ya calf?"

  • Ranked ask, capped at 1–2 filters in a single turn, never a full list.

  • Skip inferred: never ask a filter that D1 / D4 already answers — apply it silently on landing.

  • Post-apply reveal: after B2a apply, offer next-most-important filter: "Ab fabric bata do, 5 tak aa jayenge."

Silent-when.

  • Result count is already below decision-threshold (default: 20).

  • User is comparing / in a specific item, not browsing.

  • Every top-ranked filter is either applied or inferred.

Guardrails.

  • Threshold for "broad enough to nudge" is a config knob per sscat, not one number.

  • Do not ask more than one filter-elicitation question per two turns.

  • If user ignores an elicitation twice, stop asking that filter this session.

B4 — Variant swap in-place on PDP [P0]

Trigger. User is on PDP. Utterance names a variant attribute value ("blue mein", "L size mein", "print wala") that maps to an existing variant on the same product.

Precedence. Wins over B1 whenever the constraint is variant-satisfiable.

Action. Update the selected variant on the current PDP — swap colour swatch, size chooser, gallery image, price, delivery ETA — without leaving the PDP.

Consumption shapes.

  • Announce: "Blue variant dikha rahi hoon."

  • Silent swap on unambiguous single attribute if user is clearly mid-decision.

  • Bundle-announce: "Blue L select kar diya — ₹499, Fri tak."

  • OOS-fallback: "Blue-L stock mein nahi — Navy-L hai, dikhaun ya similar search karun?" (escalation offer to B1.)

Silent-when.

  • Utterance is about product opinion, not variant.

  • Named variant is already selected.

Guardrails.

  • Confirm before swap if price delta > ₹50 or delivery date changes: "Blue mein ₹40 extra hai — theek?"

  • Always narrate the new price and ETA on swap.

  • If variant does not exist and is not OOS but simply absent → escalate to B1 with the constraint carried over.

B7 — Progressive relaxation on 0 (or thin) results [P0]

Not user-triggered — an automatic fallback that fires whenever B1 / B2a / B3 leave the result set at 0 or below a thin-threshold.

Action. Identify the lowest-importance dimension in the current filter set using B2b intel, relax it by one step (price band up 10%, length adjacent bucket, colour → same colour family), re-run, narrate.

Consumption shapes.

  • Announced relaxation: "Blue mein ₹400 tak nahi mila — ₹450 tak dikhaya."

  • Two-way choice at hard walls: "Ya toh price thodi badhao ya colour badlo — kya karun?"

  • Chained-fallback narration when 2 dims relaxed: "Blue ₹400 tak khaali tha — ₹450 aur navy bhi include kar diya."

Guardrails.

  • Max 2 auto-relaxations per turn; on 3rd zero-result cycle, hand back to user.

  • Never relax a constraint the user explicitly emphasized ("sirf blue", "under 500 only") — those are locked; if 0 results, ask, don't relax.

  • Always announce which dimension was relaxed.

B3 — Sort-order steering [P1]

Trigger. Utterance implies a preferred ranking dimension: "sasta", "sabse popular", "achhi rating wala", "naya launch".

Action. Change the current sort on the feed; do not remove filters. Announce the sort change.

Data dependencies. Same B2b-style intel: which sort matters most per sscat / state.

Consumption shapes.

  • Apply-and-announce: "Price low-to-high laga di."

  • Toggle context: "Rating pe sort kar diya — 4+ rated pehle."

  • Combined with filter: if user says "sasta + blue" → apply price sort AND colour filter, narrate both.

  • Silent-when: user is on PDP (sort is CRP-only).

Guardrails.

  • Single sort dimension at a time (Meesho constraint).

  • If user says "sasta" on a broad, unfiltered CRP → suggest a filter too: "Price sort laga di — length bhi bata do?"

B5 — Size auto-select on PDP [P1]

Trigger. User lands on PDP, size not yet chosen, and we have a confident size recommendation from Context D1 / D2.

Action. Pre-select the recommended size in the size chooser, so the user only confirms rather than picks.

Consumption shapes.

  • Announce the pre-select: "Pichhle kurte ke hisaab se L select kar li — check karlo."

  • With rationale from return history: "Pichli baar M chota laga tha — L pre-selected."

  • Adjustment offer: "L lagi hai, M chahiye toh badal do."

  • Silent-when: confidence below threshold (never silently commit user to a size).

Guardrails.

  • Always narrate the pre-selection in the same turn; never silent.

  • If user overrides the size, update D1 / D2 immediately — do not re-suggest same size next session.

  • Do not pre-select if seller has known size-drift issues for this sscat unless we account for it.

B6 — Exclusion filters via chat [P2]

Trigger. Negative-form utterance: "ye seller nahi chahiye", "XS mat dikhao", "polyester wala hata do", "isse mehnga mat dikhao".

Action. Apply an exclusion (anti-filter) to the current feed. Exclusion persists across turns within the session, does not persist cross-session unless user says "hamesha ke liye".

Consumption shapes.

  • Announce: "Is seller ke products hata diye — ab 38 dikh rahe."

  • Multi-exclusion narration: "Polyester + XS hata diye."

  • Session-level reset: "sab wapas dikhao" → all Vaani exclusions cleared.

  • Cross-session promotion: on repeat exclusion of the same seller/attribute in 2+ sessions → propose promoting to persistent preference.

Guardrails.

  • Cap session exclusions at 10 items / attributes; oldest evict.

  • Expose current exclusions to the user on ask: "kaunse hata rakhe hain?"

  • Do not exclude sellers with trusted-seller flag silently — confirm once.

B8 — Return-window agentic action [P2]

Trigger. On order-state turn. User complains about a delivered item that is inside its return window. Complaint patterns: "chota hai", "kharab quality", "colour alag hai", "size nahi aa raha".

Action. Offer to initiate a return request agentically. On explicit user confirmation, submit the return with the appropriate reason code. Do not submit without confirmation.

Consumption shapes.

  • Offer: "Chota hai — 3 din return window bacha hai. Return request kar deti hoon, ok?"

  • Confirmation-gated submit: only proceed on "haan / kar do / ok / OK".

  • Reason-code narration: "Size-related return laga rahi hoon."

  • Post-submit: "Return request lag gayi — pickup Wed tak."

  • Outside-window branch: if outside window, do not offer — instead surface seller-rating / re-purchase paths.

Guardrails.

  • Never auto-submit without explicit confirmation from the same turn or the next.

  • Do not act on vague complaints ("theek nahi hai") — ask for the reason first, then offer.

  • If item has multiple units, ask which unit before submitting.

  • Log the return-reason so Context D5 (user return history) updates immediately.

4. Cross-cutting principles

  • Every agentic action announces itself. Silent behaviors are only allowed when the user's intent is single-constraint unambiguous and the change is small; even then, an announcement in one line is the default.

  • Undo is a first-class gesture. "wapas hata do", "pehle jaisa karo", "cancel" must work on every filter / sort / variant swap.

  • No dead-ends. Every behavior with a 0-result branch must connect to B7 or a clarifier — never end a turn with "nothing found".

  • Deterministic parse over LLM freelancing. Utterance → filter / constraint / variant mapping must come from an authored lexicon, not the LLM inventing filters. LLM's job is understanding + narration, not schema decisions.

  • Silent-when is as specified as trigger-when. Every behavior above defines when it does NOT fire. That specification is enforcement, not commentary.

  • Every agentic action must be observable. Log: behavior_id, trigger utterance, parsed intent, action taken, result count / outcome. This is what closes the loop into Context H2 (cross-session memory).
