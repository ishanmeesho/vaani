Vaani UX — Priorities for This Cycle

Sharing top-of-mind priorities on Vaani UX so we can close on scope for the next design cycle.

Where we are

Vaani's capabilities are stacking fast new information sources, and a set of agentic actions (variant swap, image-anchored search, filter apply, sort steering, size pre-select, exclusion filters, return-window action) landing over by this cycles. Tech will be unblocking these capability. What we need to parallely focus on is UX shell around how Vaani sits on screen, how it hands off between voice and touch, and what happens when it isn't 100% sure what the user wants.

If we keep shipping capability without design we will not realise better outcomes, so we will have to capture all behaviour we plan to solve in next 1-2 cycle. The capability → outcome conversion is 90% design. This workstream should build the shell.

What's breaking today

1. The native ASR overlay is the single biggest drag on experience. The moment a user starts talking, the screen gets blocked. Whatever we do next, this pattern has to go. Question: what does the voice-input experience look like without a full-screen overlay?

2. Vaani's positioning conflicts with every other thing on screen. On feeds and PDP, across idle / active / active-in-use states, Vaani collides with sale banners, Advanced Popup and toasts. It's bad for Vaani and equally bad for those props. We need a positioning system, not per-screen fixes.

3. Disambiguation is the next hard problem. Now that Vaani will take real actions on the user's behalf, we won't always know with high confidence which action they want. "Blue mein dikhao" — variant of this product, or new search? "Sasta kar do" — sort or filter? Some of this we'll fix with better models prompting over 1–2 cycles, but most of it has to be UI — a fast visual confirm / correct / shortcut layer that avoids either mis-firing an action or making the user speak everything twice.

4. Introduction / first-run. I want to park this. Intro will only land well once we have a defensible "Vaani helped me" moment. We will focus on building capability / behaviour with good outcomes and then figure out best way to introduce it. As of now we should solve for people who are already introduced to it and see that their outcomes improve.

The four objectives — and what each needs from us

  • Awareness ("what all can I even use Vaani for") — voice nudges + conversation design surfacing capability; proper feature intro later.

  • Adoption (first use) — voice nudges + visual placement / entry-point clarity.

  • Repeat engagement (2nd, 5th, 20th use) — same as adoption + response quality.

  • Outcomes (did Vaani actually solve the mission) — disambiguation UI + ease-of-action UI + ease-of-info-consumption UI.

The last one is where design 10xs the product. Design principle for this cycle: the pattern library should be capability-agnostic and durable across every agentic behavior we'll ship in the next 4 cycles. No custom UI for variant-swap that we can't reuse for image-search. Capability keeps stacking; the shell should not need a redraw each time.

Scope for this cycle — three things to close

1. Vaani's permanent home on Meesho, for Discovery & Decision-Making missions

  • Where does Vaani live on Home / CRP / PDP / Cart / My Orders?

  • What are the states — idle, active (listening), active-in-use (responding), thinking, action-executing, error / misunderstood — and what does each look like?

  • Kill / dismiss / re-invite rules — how does user step away cleanly, and how does Vaani come back gracefully?

2. Visual experience for "pure information" use cases

The user is asking Vaani a question and getting an answer. Vaani should not block the screen — user must still see the product / feed underneath.

  • Active state (Vaani is listening) — the non-blocking pattern that replaces the ASR overlay.

  • Active-in-use (Vaani is answering, user might interrupt or tap) — reading + doing at the same time.

  • Handoff between voice and touch as a first-class flow. User starts speaking, finishes with a tap. Or starts with a tap, continues by voice. Not an afterthought.

  • Thinking / action-executing — image search or filter apply takes 2s+. What's the visual language so user doesn't think Vaani is stuck?

3. UI patterns to augment agentic behaviors

Underlying behavior list is in the companion note. For each behavior, we need a durable UI vocabulary:

  • Pre-action confirmation surface when confidence is low — "Blue L kar dun?" as a lightweight tap-to-confirm, not a text-only ask.

  • Disambiguation surface for the common splits — "variant of this vs different product", "sort vs filter", "colour A vs colour B". Two-thumbnail chooser or chip row.

  • Post-action undo affordance, visible on the surface for a short window after every agentic action.

  • Shortcut chips for common refinements — "only blue", "sasta", "aur dikhao" — so repeat users don't have to speak every time.

  • Loading / thinking / executing state (as above).

  • Failure / misfire recovery — Vaani didn't understand, action failed, results empty. Every state must have a graceful exit; no dead-ends.

A few more things I want us to think about

  • Multi-turn context indicator. How does the user know Vaani remembers the last product they looked at, the last filter they applied? A lightweight breadcrumb / anchor pattern.

  • Cross-surface consistency. Vaani on Home vs CRP vs PDP vs Cart vs My Orders should feel like the same entity, not five different Vaanis, but should adapt behavior + real estate to state.

  • Accessibility. Voice-first can be a big accessibility win if we design for it — and a regression if we don't. Worth being explicit.

  • Where visual response beats voice response. Some answers are better shown than spoken (variants, price ladder, delivery ETA, real image, size recommendation with rationale). Which of our responses default to which channel, and how do they compose?

What we want out of this exercise

  • Positioning system — where Vaani lives, how it shifts state, across the 5 surfaces.

  • Non-blocking voice-input pattern to replace the ASR overlay.

  • Reusable UI kit for agentic behaviors — confirm, disambiguate, undo, shortcut, loading, failure — that survives the next 4 cycles of capability adds.
