Vaani — Filter Application in Search

1. Context

Today Vaani can only decide whether to search on the user's behalf. Filters (color, material, price, etc.) are still user-driven on the app.

We want to extend Vaani so that in the same decision it can search + apply filters + sort whenever the user's utterance carries such intent — and then manage that state coherently across turns in a conversation.

Target retrieval pattern: search the sscat as a query, apply the rest as structured filters (e.g., search "kurti", filter color=black, material=cotton, budget<150). This preserves category context that would otherwise be lost when candidates are fetched via EBR from a compound query like "red polka dot saree".

2. What we want Vaani to do

In a single turn, given the user's utterance and current session state, Vaani should output:

  1. A search query string — the sscat term, plus any attribute the user mentioned that is not representable as a filter for that sscat.

  2. A structured filter delta — add / replace / append / remove / clear operations against the currently active filter set.

  3. A sort operation (optional) — cheapest / best-rated / etc., when the user signals it.

  4. A response-side clarifier (only for sort actions — see §6).

Routing rule: if an attribute the user mentioned is available as a filter (or sort) for the detected sscat, it goes to filters/sort. Everything else stays in the query. When an attribute is applied as a filter, it must be stripped from the query string so we don't double-constrain.

Nudges for additional filter suggestions are handled outside the response LLM (see §9).

The mapping step is the LLM call. Everything before and after is deterministic.

4. Filter operations Vaani must support

Within a single sscat context, Vaani must be able to emit any of:

OpUser signal (examples)Semantics
Add "black kurti", "add cotton" New attribute, not previously active
Replace "white main dikhao", "only under 100" User specified a value for an attribute already filtered → swap value
Append (OR) "white aur black dono", "add white also" Same attribute, additional value → keep both
Remove "any color chalega", "remove price filter" Drop that attribute
Clear "reset", "start fresh", "kuch aur dikhao" Drop all filters
Keep (no-op) Utterance is not a filter attribute for this sscat Filters unchanged; token goes to search query

The Replace vs Append distinction hinges on linguistic cues ("only", "instead", "change to" → replace; "also", "and", "dono", "or" → append). Prompt needs explicit few-shot examples for both.

Same-attribute values are OR; cross-attribute values are AND — this is a property of the filter execution layer, not something Vaani has to encode. Vaani only decides what to add per attribute.

5. Sort operations Vaani must support

Certain user signals map to sort, not filter:

SignalOp
"sasta", "cheapest", "sabse sasta" sort = price_asc
"achhi quality", "best rated", "sabse acha" sort = rating_desc
(extend as needed)

Behavior:

  • Vaani applies the sort in the same turn.

  • The response confirms the action to the user and asks a bounded clarifier, e.g.:

    • After sasta: "Maine sabse saste products dikhaye hain. Koi specific budget hai — under 100, 200, 500?"

    • After achhi quality: "Top-rated products dikhaye hain. Kya specific rating threshold chahiye — 4+, 4.5+?"

  • This is the only case where a clarifier lives inside the response LLM call. It's tied directly to the sort action, so it's not "extra work" — the LLM is already generating the response for that action.

Sort and filter can coexist (e.g., filter color=black + sort=price_asc). Sort replaces prior sort; there is no "append sort".

6. Continuity default within same sscat — with a critical exception

While the user is on the same sscat, filters accumulate incrementally across turns. But:

If the user has explicitly removed a filter value earlier in the session, Vaani must not silently re-apply it later, even if a subsequent user utterance would otherwise re-trigger it.

Example:

  1. Vaani applies color=black on kurti.

  2. User removes the black filter (via UI or by saying "any color").

  3. User later says "cotton kurti".

  4. Vaani should apply only material=cotton. It must not re-add color=black, even though it's the "last known" state (from previous turn), because the user explicitly rejected it. For current sscat filtering we should always check the current state of filter. In this case the current state would have showed us that black has been removed, so we keep it removed.

Removals are cleared only when:

  • The user explicitly asks to re-apply that filter, or

  • The session ends (app close).

7. Nudges — surfacing the next filter

We have a data source that, for a given search result set, ranks the top-N filter values users are most likely to apply next.

  • After any search action (Vaani-initiated OR user-initiated), route the top unapplied filter value through the existing delay-based nudge infrastructure. Not through the response LLM.

  • The nudge module skips filter values that are already active or in the user-removal set (§8), and walks down the priority list.

  • The nudge asks the user in natural language whether to apply it, via the existing [placeholder] templating pattern.

Nudge infra receives: {sscat, active_filters, ranked_filter_recommendations}.

Confirmed: filter suggestions do not live in the response LLM call.

8. Worked examples

  1. Fresh start with attributes User: "black cotton kurti under 150" → query: kurti, filters: +color:black, +material:cotton, +price:<150

  2. Follow-up, add constraint Prior state: sscat=kurti, filters={color:black, material:cotton} User: "100 se kam" → filters: +price:<100

  3. Follow-up, non-filter attribute User: "korean style" → query: korean style kurti, filters unchanged (korean style is not a filter value)

  4. Follow-up, replace value Prior state: filters={color:black} User: "white main dikhao" → filters: color:black → color:white

  5. Follow-up, append value Prior state: filters={color:black} User: "white aur black dono" → filters: color:{black,white}

  6. Sort — sasta User: "sasta kurti" → query: kurti, filters: {}, sort: price_asc Response: "Sabse saste kurtis dikhaye hain. Koi specific budget hai — under 200, 500?"

  7. Sort — best rated User: "achhi quality ke kurti" → query: kurti, filters: {}, sort: rating_desc Response: "Top-rated kurtis dikhaye hain. Kya 4+ rating chahiye ya 4.5+?"

  8. Sscat switch Prior: sscat=shirt, filters={color:blue, price:<500} User: "saree dikhao" → clear active state; query: saree; cache shirt → {color:blue, price:<500}.

  9. Sscat return Prior (post-8): user says "wapas shirt dikhao" → restore cached shirt filters; query: shirt; filters: {color:blue, price:<500}.

  10. Respect user removal Turn 1 — Vaani applies color=black on kurti. User removes black. State: filters={}, user_removed={color:black}. Turn 2 — User: "cotton kurti" → filters: +material:cotton only. color:black is not re-added.

  11. Explicit removal User: "any color chalega" → remove color from active filters; add color:<current values> to user_removed_values.

9. Residual scenarios / decisions

Each of these needs a call:

  1. Sscat confidence threshold. What confidence do we require before applying filters? Low confidence should degrade to plain-search-no-filters. Suggest a threshold (e.g., ≥0.7) — needs tech input on calibration or source. [I think for each search query, we already get sscat mapped to it, there is a search API for this]

  2. Attribute value not in sscat's filter dictionary. E.g., "silk" but silk isn't offered for that sscat. Fall through to query token, log for dictionary growth.

  3. Negation. "not black", "red ke alawa". v1: drop to query. Fast-follow: proper NOT filter support.

  4. Numeric range parsing. "under 100", "100-200", "around 150", "budget friendly". Needs a canonical range grammar shared between prompt and filter API.

  5. Contradictions inside one utterance. "black white but only white" — "only" overrides "and". Prompt handles via example.

  6. Manual UI filter changes mid-session. User toggles filters in the drawer between Vaani turns. Requires the app to sync active-filter state back into Vaani's context on every turn — otherwise Vaani overwrites what the user just did.

  7. Multi-sscat query. "kurti and saree under 500" — pick the dominant sscat via heuristic, or plain search, or ask a clarifier?

  8. Ambiguous follow-up. "isse acha kuch dikhao" — continue with same filters, or reset? Recommend: keep filters + apply sort=rating_desc and ask clarifier.

  9. Nudge fatigue. Cap per session; don't nudge the same filter twice; skip nudges immediately after a user dismissal.

  10. "Koi filter nahi lagao" as a meta-instruction. Should suppress filter ops for the rest of the session (or until user asks for one). Add a session-level suppress_filters flag.

10. Confirmed principles (for the KRD)

  1. Sscat as query, everything else as filter/sort. Preserves category recall.

  2. Strip filtered attributes from the query string. No double-constraining.

  3. Vaani owns state. Active filters + per-sscat cache + user-removed set live in Vaani's context. App must sync back manual UI changes each turn.

  4. User removals are sticky. A value the user removed does not come back on its own for the rest of the session.

  5. Filter suggestions go via nudge infra, not the response LLM. Sort clarifiers stay in the response (bound to the action).

  6. Session = one app-open. No further disambiguation.

  7. v1 op set: add / replace / append / remove / clear / no-op / sort. Defer negation and multi-sscat clarification.
