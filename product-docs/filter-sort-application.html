KRD — Vaani Filter & Sort Application in Search

Extending Vaani from search-only to search + filter + sort, with session-aware state management.

Section I: Executive Summary

1. Problem Statement

Vaani today can only decide whether to search on the user's behalf. Filters and sort remain user-driven on the app. Every search-like turn ("black cotton kurti under 150", "sasta saree dikhao", "white main dikhao") is collapsed into a raw text query, which loses category recall (compound-attribute queries under-serve sscat retrieval).

This KRD ships the capability that lets Vaani, in the same turn, resolve the sscat, decide the filter and sort operations to apply against the current session state, and emit a strip-clean search query. It also defines the session-scoped state (per-sscat cache, user-removed set, suppress-filters flag) that keeps that behavior coherent across turns, and the dependencies on the sscat resolution API, the filter dictionary per sscat, and the app-to-Vaani state sync that engineering must build.

2. Product Thinking

The instrumented Vaani we shipped told us that habit-formed users lean heavily on FIND turns (81.8% of habitual turns; six sticky FIND sub-moves carry the surface). Filter application is the single most common act these users perform after seeing search results. Today Vaani abandons them at that step. Three claims we want the launch to support or reject:

  • Structured filter/sort raises the ceiling on Vaani search turns. A Vaani turn that emits filters/sort should convert more (click-through, session order rate, ITT) than a Vaani search-only turn, because it lands the user closer to intent-matched inventory.

  • Sscat-as-query preserves category recall. EBR retrieval compound queries lose category context; sscat-as-query + structured filters recovers it. Text-search fallback rate should fall on Vaani turns where this pattern applies.

  • State-aware filter continuity is a habit accelerator. Auto-restoring last-known filters on sscat return, and respecting user-removed values, prevents the "Vaani keeps re-applying stuff I removed" frustration pattern that would otherwise emerge the moment filters ship.

2. Scope

2.1 In Scope

  • Per-turn Vaani output extended from a single search_query string to a structured object: { search_query, filter_ops[], sort_op?, response_clarifier? } — see 3.1.

  • Seven filter operations: add, replace, append (OR-within-attribute), remove, clear, no-op; plus one sort_op per turn. Sort dictionary extendable (v1: sasta → price_asc, achhi quality → rating_desc). Full catalogue in 3.1.

  • Session-scoped Vaani state: current_sscat, active_filters, active_sort, sscat_cache, user_removed (per sscat), suppress_filters. See 3.2.

  • Auto-strip: attributes applied as structured filters are removed from the search_query string in the same turn. No double-constraining. See 3.3.

  • Cross-sscat behaviour: sscat switch clears active state and caches prior; sscat return in the same session restores cache. See 3.4.

  • User-removal stickiness: a value the user explicitly removed does not auto-reapply for the rest of the session. See 3.5.

  • Nudge integration: after every search action (Vaani- or user-initiated), the delay-based nudge infra receives the current state and fires a delayed next-filter suggestion. Filter suggestions do NOT live in the response LLM. See 3.6.

  • Sort clarifier (in-response): after sasta / achhi quality, the response asks a single bounded clarifier. This is the only clarifier permitted inside the response LLM. See 3.7.

  • App → Vaani filter-state sync every turn: the app pushes the current active filter/sort state (including any manual drawer toggles) into Vaani's context at the start of every Vaani turn. See 4.

  • Instrumentation for every op emitted, every state transition, and every nudge fire. See 7.

  • A/B experiment plumbing: Treatment (filter+sort enabled) vs Holdout (Vaani search-only, current). See 5.

2.2 Out of Scope

  • Prompt / intent changes — shipped in a separate KRD.

  • Negation filters ("not black", "red ke alawa") — v1 drops to search_query; proper NOT support is a fast-follow.

  • Multi-sscat clarification turn ("kurti and saree under 500") — v1 uses dominant-sscat heuristic (first mentioned) and puts the other in the query.

  • Cross-session persistence of the sscat cache — cache lives per app-open only.

  • Free-form range queries beyond the canonical grammar defined in 4. "Under 100", "100-200", "around 150" supported; open-ended arithmetic is not.

  • New UX surfaces (e.g., a filter-chip strip generated by Vaani) — filters are applied against the existing filter service; the UX layer is unchanged.

3. Product Decision Framework

3.1 Operation Catalogue (Filter & Sort)

Every op below carries: trigger cues, semantics, and priority. Same-attribute values are OR; cross-attribute values are AND — enforced by the filter execution layer, not by Vaani.

Filter operations

IDPriorityOpTrigger cuesSemantics
F1 P0 add "black kurti", "add cotton" New attribute, not previously active. Push value onto the attribute's value set.
F2 P0 replace "only", "instead", "change to", "-hi dikhao" Same attribute already active. Overwrite the value set with the new value(s).
F3 P0 append (OR) "also", "and", "dono", "or", "aur" Same attribute already active. Add the new value to the existing value set.
F4 P0 remove "any X", "remove X", "koi bhi X" Drop the attribute. All previously-active values for that attribute are pushed into user_removed for the current sscat.
F5 P0 clear "reset", "start fresh", "kuch aur dikhao" Drop all filters and sort. Does NOT populate user_removed (clear is a fresh start, not a targeted rejection).
F6 P0 no-op Utterance not a filter attribute for this sscat Filters unchanged. Token stays in search_query. Log fall-through for dictionary growth.

Sort operations

IDPrioritySignalSort opResponse clarifier
S1 P0 "sasta", "cheapest", "sabse sasta" sort = price_asc "Maine sabse saste products dikhaye hain. Koi specific budget hai — under 100, 200, 500?"
S2 P0 "achhi quality", "best rated", "sabse acha" sort = rating_desc "Top-rated products dikhaye hain. Kya specific rating threshold chahiye — 4+, 4.5+?"
S3 P1 (extendable dictionary — latest, popular, newest, discount%) — Dictionary owned by PM + search; extendable without code change.

  • Sort applies in the same turn as the utterance. Sort replaces prior sort — there is no "append sort".

  • Sort + filter coexist (e.g., filter color=black + sort=price_asc). If sort=price_asc coexists with filter=price:<X (explicit user budget), both apply — sort ascending within the budget.

  • The sort clarifier is the only clarifier permitted inside the response LLM. All other filter suggestions go through the nudge infra (3.6).

3.2 Session State Contract

Vaani owns state. Every Vaani turn is invoked with the following session-scoped object; the response LLM reads it, and the orchestrator writes the delta back at turn end.

SessionState {

current_sscat: string | null,

active_filters: Map<attribute, Set<value>>, // e.g. {color: {black}, material: {cotton}}

active_sort: SortOp | null,

sscat_cache: Map<sscat, {filters, sort, user_removed}>,

user_removed: Map<attribute, Set<value>>, // sticky for current sscat, session-scoped

suppress_filters: boolean

}

  • active_filters, active_sort, and user_removed are scoped to current_sscat.

  • On sscat switch: (a) write current active_filters/active_sort/user_removed to sscat_cache[old_sscat]; (b) reset active state; (c) load sscat_cache[new_sscat] if present.

  • user_removed for a given attribute is cleared only when (i) the user explicitly re-applies that attribute in the same session, or (ii) the session ends.

  • suppress_filters is toggled true when the user says a meta-instruction like "koi filter nahi lagao". Toggled off when the user asks for a filter again or the session ends.

  • Session = one app-open. All state persists for the app-open duration and resets on app close.

3.3 Query-Stripping Rule

  • Whenever an attribute is applied as a structured filter, that attribute must be stripped from the search_query string in the same turn.

  • search_query in v1 = sscat term + any residual attribute tokens (those NOT representable as a filter/sort for this sscat).

  • Example: user says "black kurti" → search_query = "kurti"; filter_ops = [+color:black]. Not "black kurti" + [+color:black].

3.4 Cross-Sscat Behaviour

  • On switch (shirt → saree): clear active_filters and active_sort. Fresh sscat, fresh slate. Prior sscat filters/sort/user_removed are cached in sscat_cache.

  • On return in the same session (saree → shirt): auto-restore the cached filters, sort, and user_removed for shirt.

  • sscat_cache lives for the session (app-open) only.

3.5 Continuity & User-Removal Rule

Within the same sscat, filters accumulate incrementally across turns unless the user explicitly asks to remove or replace them — with one critical exception:

If the user has explicitly removed a filter value earlier in the session (via Vaani or via the manual filter drawer), Vaani must NOT silently re-apply it later, even if a subsequent user utterance would otherwise re-trigger it. The current filter state (which reflects the removal via app-to-Vaani sync) is the source of truth. The user_removed set is a defence-in-depth backstop.

3.6 Nudges — Next-Best Filter Suggestion

  • After every search action (Vaani-initiated OR user-initiated), the delay-based nudge infra is passed the search context and fires a delayed suggestion for the next unapplied filter.

  • Filter suggestions do NOT live in the response LLM call. Rationale: keeps the response fast and single-purpose; delay / templating / dismissal already exist in nudge infra.

  • The nudge module must skip any filter value that is already in active_filters OR in user_removed for the current sscat. It walks down the priority list to the next unapplied, non-rejected value.

  • Nudge infra payload from Vaani: { sscat, active_filters, active_sort, user_removed, ranked_filter_recommendations }.

3.7 Sort Clarifier (in-response, bounded)

  • Only after S1 (sasta) or S2 (achhi quality), the response emits one bounded clarifier asking for a specific budget / rating threshold.

  • Clarifier is not asked when sort coexists with an explicit user filter (e.g., "500 tak sasta kurti" → sort applied, no clarifier because budget is already specified).

  • This is the ONLY clarifier permitted inside the response LLM. All other suggestions must go through nudge infra (3.6).

4. Technical Requirements — Data & System Dependencies

The remainder of this section is what engineering needs to build against. Detailed solutioning goes in 6.

4.1 Source APIs & Dependencies (assumed pre-existing)

SourceGrainUsed byNotes
sscat_resolution_api utterance → sscat_id, confidence Vaani turn front-half Ishan: "for each search query we already get sscat mapped to it." Confidence field to be exposed.
filter_dictionary_api sscat_id → available filters, values, sort options Vaani turn front-half Needs to be exposed to Vaani; must include sort dictionary and range grammar per attribute.
active_filter_state user × session → current filters + sort Every Vaani turn App-side; must be synced into Vaani context at turn start (see 4.3).

filter_recommendation_ranker search result → top-N filter values nudge infra input Existing data source (top-x filter values users are likely to apply). Must be able to accept & honour Vaani's user_removed set.

4.2 Filter Dictionary Contract

  • Per sscat_id, Vaani must be able to fetch: list of available filter attributes; acceptable values (or value grammar for numeric ranges); whether the attribute supports OR (same-attribute multi-value); list of available sort options; canonical mappings from user cues (sasta, achhi quality, latest, popular …) to sort ops.

  • Attribute values the user mentions that are NOT in the sscat's dictionary fall through to search_query. Every such fall-through is logged so the dictionary can be grown.

  • Numeric-range grammar (canonical; shared between Vaani prompt few-shot and the filter API): { op: "lt" | "lte" | "gt" | "gte" | "between", value: number | [number, number] }. Phrases: "under 100" → {lt, 100}; "100 se kam" → {lt, 100}; "100-200" → {between, [100,200]}; "around 150" → {between, [135,165]} (±10% band, tunable).

4.3 App → Vaani State Sync Contract

  • The app must sync the current active filter and sort state — including any manual toggles the user made in the filter drawer since the last Vaani turn — into Vaani's context at the start of every Vaani turn.

  • If the user has cleared a filter in the UI between Vaani turns, Vaani reads it as removed in the incoming payload. Vaani must not silently re-apply it (see 3.5). The clearing must also push the cleared values into user_removed for that sscat.

  • This is a hard dependency. Without it, Vaani will overwrite user actions. Recommendation: turn-start payload push (not polling).

4.4 Sscat Confidence Threshold

  • Vaani applies filters and sort only when sscat confidence ≥ threshold. Default: 0.7 (needs calibration on live sample; see 8).

  • Below threshold → plain search on the raw utterance; no filter_ops, no sort_op. This preserves current behaviour on ambiguous queries.

4.5 Vaani Turn Output Contract

The response LLM emits, per turn:

{
  search_query: string,          // sscat term + residual (non-filterable) attribute tokens
  filter_ops:  FilterOp[],       // add | replace | append | remove | clear (0..n)
  sort_op:     SortOp | null,   // 0 or 1
  response_clarifier: string?    // only when sort_op is set (3.7)
}

  • The orchestrator applies filter_ops and sort_op against the current SessionState (3.2) and forwards search_query + resulting filters + sort to the filter execution service.

  • State delta is persisted back to SessionState at turn end.
