Vaani — Context Enrichment Product Note

Owner: Ishan Sharma Status: Draft for alignment (pre-KRD) Scope: Additional data/context fields to inject into Vaani so that responses become materially more useful across turns (primary focus: DECIDE / PDP turn; applicable to home, SRP, order-state turns where noted).

1. Purpose

Vaani today answers with generic language because it lacks grounded, per-user, per-product, per-region signal. This note enumerates every field we want to add, and — critically — every shape in which that field can be consumed inside a prompt. The "shape" list is what turns a raw number into a magic sentence. The KRD that follows this note will map each field to Layer-1 (always-in-context) or Layer-2 (tool-fetched on demand).

2. Principle: field × shape is the unit

For every field we add we must know:

  • What it is (definition, source, granularity).

  • All shapes in which the LLM can consume it — absolute, comparative, sliced, framed, silent-when.

  • Trigger — when Vaani should surface it, when it should suppress it.

  • Guardrails — data-thinness thresholds, staleness, privacy.

A field with no defined shape is dead weight in the context window.

3. Data clusters

Cluster A — Seller & Product Trust

A1. Product return rate (lifetime, 30d, 90d)

  • Definition: % of delivered units returned. Report 3 windows: L30D, L90D, lifetime.

  • Shapes:

    • Absolute: "Return rate 12%."

    • Comparative vs sscat median: "12% vs category norm 22%."

    • Comparative vs seller's other products: "Lower than 8 of this seller's 10 products."

    • Trend: "Return rate has dropped from 18% → 12% in 30 days."

    • Reassurance framing: "4 out of 5 buyers keep it."

    • Warning framing: "1 in 4 buyers return this — pick size carefully."

    • Silent-when: within ±5pp of sscat median AND no trend movement → do not mention.

A2. Return reason breakdown (NEW — approved)

  • Definition: Distribution of return reasons for this product. Buckets: size/fit, quality, wrong item, damaged, colour mismatch, changed mind, delivery delay.

  • Shapes:

    • Dominant reason callout: "Most returns are size-related, not quality."

    • Quality-share isolation: "Only 3% of returns are quality issues."

    • Fit-warning: "60% of returns are size-related — let me help you pick."

    • Category-relative: "Colour-mismatch returns higher than sscat avg by 8pp."

    • Silent-when: no reason exceeds 25% share (i.e. no dominant story).

A3. Variant-level return rate (NEW — approved)

  • Definition: Return rate per (colour × size) variant.

  • Shapes:

    • Variant-specific warning: "Red-XL returns 30% vs Blue-L at 6% — worth a look."

    • Steering: "Users who bought Blue-M rarely return; Red-M returns more."

    • Blended with reason: "Red-XL returns are mostly 'colour looked different' — real image will help."

    • Silent-when: variant sample < 100 units delivered.

A4. Lifetime orders on product

  • Shapes:

    • Popularity signal: "3.2 lakh people have bought this."

    • Freshness signal: "Just launched — 240 orders so far."

    • Trust anchor: "One of the top 5% ordered in this sscat."

    • Silent-when: < 50 orders (too thin to boast).

A5. Seller tenure on Meesho

  • Shapes:

    • Absolute: "This seller has been on Meesho for 4 years."

    • Trust anchor: "Long-standing seller (5+ yrs)."

    • Caveat framing for new sellers: "New seller — but trusted flag is on."

    • Silent-when: tenure between 1–3 yrs and no other trust story.

A6. Trusted-seller flag

  • Shapes:

    • Direct: "Trusted seller badge."

    • Combined with returns: "Trusted seller and low return rate."

    • Silent-when: flag off (never call attention to absence).

A7. Seller rating (avg + count)

  • Shapes:

    • Absolute: "Seller rated 4.3 across 1.2 lakh reviews."

    • High-confidence anchor: "4.3 rating on 1L+ reviews — very stable."

    • Low-count caveat: "Rating 4.6 but only 40 reviews — early signal."

    • Silent-when: rating < 3.8 (don't lead with weak signal, but do not hide if asked).

A8. Seller-level bad-quality return rate

  • Definition: % of this seller's returns tagged 'bad quality' across all their products.

  • Shapes:

    • Trust reinforcement: "Only 4% of this seller's returns are quality-related."

    • Warning: "1 in 3 returns from this seller are quality issues."

    • Silent-when: within ±3pp of platform median.

Cluster B — Social Proof

B1. Positive review theme summary

  • Definition: Pre-computed thematic tags with weights: fit, fabric, colour-accuracy, packaging, value, delivery, stitching. Never raw quotes — themes with %.

  • Shapes:

    • Top theme: "Most praised: fabric feel."

    • Multi-theme: "Buyers loved fabric and packaging; colour got mixed feedback."

    • User-context match: "Reviewers your size praised the fit."

    • Silent-when: fewer than 20 reviews.

B2. Negative review theme summary

  • Shapes:

    • Honest surface: "Main complaint is stitching on sleeves."

    • Mitigation framing: "Some complained of colour mismatch — real image is available."

    • Category-relative suppression: "Negatives are typical for this category — no unusual issues."

    • Silent-when: negative themes below platform-median share.

B3. Photo-review count and thumbnails available

  • Shapes:

    • Count: "127 buyers uploaded photos."

    • Action prompt: "Want to see buyer photos?"

    • Silent-when: photo review count < 10.

B4. Users-like-you cohort feedback

  • Definition: Reviews filtered by cohort (region + budget-band + sscat history overlap). Requires min cohort size.

  • Shapes:

    • Cohort echo: "Buyers from Bihar in your budget mostly kept it."

    • Cohort divergence: "In your region this fits differently — most sized up."

    • Cohort-specific reason: "Users like you returned mostly for size, not quality."

    • Silent-when: cohort < 200 orders in last 90 days.

    • Guardrail: define cohort key upfront; do not fabricate if thin.

Cluster C — Visual Truth

C1. Real-image existence flag

  • Shapes:

    • Direct offer: "A real photo of this product exists — want to see?"

    • Trust boost: "Verified real image available."

    • Comparative: "Real image differs slightly from catalog on colour."

    • Silent-when: flag false.

C2. Variants + variant attributes

  • Definition: List of (variant_id, colour, size, price_delta, stock_flag, image_url, per-variant return rate — see A3).

  • Shapes:

    • Enumeration: "Available in Red-M, Red-L, Blue-M, Blue-L."

    • Recommendation-shaped: "Blue-L is the most-ordered by users your size."

    • Comparison: "Red is ₹40 cheaper, Blue has better reviews."

    • Cross-link to real image per variant if available.

Cluster D — Personalization (User)

D1. sscat-level size preference

  • Shapes:

    • Passive prefill: "You usually pick L in tops — L is available."

    • Steering: "Users your size in this seller often size up — try XL."

    • Silent-when: no preference known for this sscat.

D2. Size derived from past-order history + fit signal

  • Definition: For sscat, look at last N orders in similar sub-category, join with return-reason. If prior returns tagged 'small', bias up.

  • Shapes:

    • Direct recommendation: "Based on your last kurta (M, kept), M should fit."

    • Adjustment recommendation: "You returned last one for being small — try L this time."

    • Uncertainty framing: "Sizes vary by seller — this one runs small, size up."

    • Silent-when: no past order in near-adjacent sscat.

D3. Name and gender slot

  • Guardrail-first field. Indian-name→gender inference is unreliable. Preferred source: order history skew; name is fallback only.

  • Shapes:

    • Address by name (rare, opening turn): "Ishan ji, ..."

    • Gender-agnostic default in ambiguous cases.

    • Correction handling: if user corrects, overwrite slot for whole session AND persist.

    • Silent-when: confidence below threshold.

D4. sscat-level budget band

  • Shapes:

    • Price framing: "This is in your usual range for kurtas."

    • Splurge framing: "Slightly above your usual — but return-safe seller."

    • Value framing: "Below your usual band — worth trying."

    • Silent-when: no budget history for sscat.

D5. User's own return history + repeat-returner flag

  • Definition: User's lifetime return rate, and return-reason mix.

  • Shapes:

    • Sensitive tone-shift: for high returners, avoid over-promising returnability; emphasize fit accuracy.

    • Sizing extra-care: if user returns often for size, aggressively confirm size before add-to-cart.

    • Empowerment framing: "Return window is safe, and this seller processes returns fast."

    • Never surface the return-rate number directly to the user. Internal signal only.

Cluster E — Commercial Context

E1. Regional/state/city orders in last N days

  • Definition: Orders in user's pincode, city, state, region over 3, 7, 30 days.

  • Shapes:

    • Pincode-tight: "27 people in your pincode ordered this in the last 7 days."

    • City-level: "Trending in Patna this week."

    • State-level: "Popular across Bihar."

    • Region-level fallback if smaller granularities thin.

    • Momentum: "Orders in your city are up 3x this week."

    • Silent-when: < 5 orders at chosen granularity.

E2. Delivery ETA to user + area typical lead time

  • Shapes:

    • Specific date: "Delivery by Sat, 18 Jul."

    • Range: "Usually reaches your area in 3–5 days."

    • Compare-to-average: "Faster than typical for your pincode."

    • Sale-day caveat: "Sale week may add 1 day."

    • Trust anchor: "This seller ships within 24 hrs to your zone."

E3. Price ladder (prepaid / return-type / bank offers)

  • Definition: All conditional price points as a structured object: base, prepaid_price, non_returnable_price, coupon_price, bank_offer_price.

  • Shapes:

    • Choice framing: "₹499 base, ₹479 on prepaid, ₹459 if you skip return."

    • Best-price anchoring: "Cheapest is ₹459 with prepaid + no-return."

    • Trade-off framing: "₹20 less if you go non-returnable — but return rate here is 12%, so think twice."

    • Silent-when: no conditional variants exist.

E4. Zonal discount attribution

  • Definition: If price is discounted because seller-zone matches user-zone, expose the delta.

  • Shapes:

    • Attribution: "₹40 cheaper because seller is in your zone."

    • Reason-for-price framing: "Price is low because zonal seller — quality is not compromised."

    • Silent-when: no zonal component.

E5. Price trend (this product on Meesho)

  • Definition: Time series of listed price. Report last 30 / 60 / 90 day min/max/current.

  • Shapes:

    • At-low: "Lowest price in 60 days."

    • Small-move: "Was ₹520 last week, ₹499 today."

    • Sale-adjacent: "Was ₹499, dropped to ₹449 for today's sale."

    • Stable: silent.

    • Silent-when: variation < 3%.

E6. Sale calendar (first-Sunday-of-month + campaign flags)

  • Shapes:

    • Today-is-sale: "Today's the monthly sale — prices are at their lowest."

    • Sale-in-N-days: "Sale is in 3 days if you can wait."

    • Missed-sale framing (short window after): "Sale just ended, but this is still ₹30 below last week."

    • Category campaign overlay: "Ethnic-wear campaign live till Sunday."

E7. COD / payment eligibility at pincode (NEW — approved)

  • Shapes:

    • Availability: "COD available at your pincode."

    • Restriction: "COD not available here — prepaid only."

    • Steering: "Prepaid gives ₹20 off anyway."

    • Silent-when: user has payment preference already set as prepaid and COD is available (not decision-relevant).

Cluster F — Order State

F1. Undelivered orders (in transit)

  • Definition: List of open orders with (order_id, product, current_status, expected_date, deviation_from_promise).

  • Shapes:

    • Direct answer: "Your kurta order arrives Friday, on track."

    • Delay flag: "Your saree is 1 day behind promise."

    • Deep-link to My Orders on ask.

    • Aggregate: "3 orders in transit, all on time."

F2. Delivered orders in return window

  • Definition: Orders delivered in last 7/10 days (return window varies). Report days-left.

  • Shapes:

    • Time-sensitive reminder if user asks: "2 days left on your kurta return window."

    • Rating nudge if unrated.

    • Deep-link to My Orders → item.

F3. Delivered orders outside return window

  • Definition: All lifetime orders, with: order date, rating given, returned? return reason, return outcome.

  • Shapes:

    • Reference for size recommendation (feeds D2).

    • Reference for repeat-returner flag (feeds D5).

    • User-facing on ask: "Your last kurta from March — rated 4, kept."

    • Sscat memory: "Last 3 t-shirts you bought were all size M, all kept."

Cluster G — Alternate Products (NEW — approved)

G1. Similar-price better-signal alternatives

  • Definition: Top 3–5 products in same sscat within ±15% price, ranked by (rating × orders × 1/return_rate), filtered to user's size availability.

  • Shapes:

    • Silent offer: "There's a similar one at ₹40 less with a 4.3 rating — want to see?"

    • Return-safer alternative: "Same price, half the return rate — worth a look."

    • Same-seller alternative: "Same seller has a very similar one that fits better for your size."

    • Cohort-anchored: "Buyers like you often picked X over this."

    • Trigger only when: user shows hesitation, asks comparison, or the current product has a warning signal (high return, low variant stock).

    • Silent-when: user has explicitly said "isko hi lena hai" or added to cart.

Cluster H — Memory & References

H1. In-session product-view stack

  • Definition: Last 5 products viewed in this session, with (product_id, sscat, price, colour, timestamp).

  • Shapes:

    • Deictic resolution: "wo laal wali" / "jo pehle dekha tha" → resolve to product_id from stack.

    • Comparative on demand: "Isse pehle waali sasti thi lekin rating kam thi."

    • Cross-product delta: colour, price, seller comparison.

    • Resolver required — plain string match will fail on Hindi/mixed queries.

H2. Cross-session lightweight memory

  • Definition: Per user, an append-only table keyed by (sscat, question_intent) → {last_response_pattern, session_outcome: cart|no_cart}.

  • Question intents to start with: "is quality good", "will it fit", "is delivery fast", "worth the price", "return easy".

  • Shapes:

    • Response-pattern recall: for repeat intent in same sscat, retrieve last pattern; if last outcome=cart, reuse; if no_cart, try a different pattern.

    • Preference reinforcement: "Last time you asked me about quality on kurtas, we looked at reviews — want me to do the same here?"

    • Do NOT store the raw response — store the pattern tag (e.g., "led-with-return-reason-breakdown").

    • Guardrails: cap at 200 rows per user, TTL 90 days, no PII.

4. Cross-cutting notes

  • Silent-when rules are as important as surface rules. Every field must define when Vaani does NOT mention it, else the context window fills with noise.

  • Cohort/thinness thresholds must be explicit per field. No field should be surfaced with sub-threshold sample.

  • All numeric fields must arrive rounded and unit-tagged (percent, INR, days) — the LLM should not do arithmetic to reformat.

  • Every field must have a "framing library" — reassurance / warning / neutral phrasings, so we control tone consistency and don't let the LLM freelance.

Next step: once we align on this list and the shapes, we'll move to the KRD mapping every field to Layer 1 (always-in-context) vs Layer 2 (tool-fetched), with latency budgets and staleness rules.

Priority tiers

  • P0 — must have for launch. High DECIDE-turn impact, moderate build cost. 21 fields.

  • P1 — cycle 2. High value but heavier compute, wider data dependency, or waits on P0 primitives. 10 fields.

  • P2 — directional. Advanced / needs careful design or new stores. 2 fields.

Notes for backend team

  • Every numeric field must arrive rounded and unit-tagged (percent, INR, days). Vaani should not reformat.

  • Every field must respect its silent-when threshold (defined in Section 4). If sample is thin, return null, not a low-confidence value.

  • Freshness expectations: aggregates in A / B / E1 / F3 / G1 can be daily-batch. C3 variants, F1 / F2 orders, E2 ETA, E3 price ladder, E6 sale calendar must be real-time / near-real-time. H1 session stack is per-session in-memory.

  • Cohort keys for B4 and G1 to be locked before build — proposed: (region + budget_band + sscat_history_overlap).
