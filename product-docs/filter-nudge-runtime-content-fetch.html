KRD — Vaani Filter Nudge with Runtime Content Fetch

Post-search delay-based filter/sort suggestion nudges, with content resolved at trigger time by the backend against the user’s current search context.

Section I: Executive Summary

1. Problem Statement

Meesho’s current nudge infrastructure is start-of-session bound: at app open, the backend ships the client the full set of triggering rules (rule_ids with parameters) AND the nudge content payloads for every rule the user is eligible for that session. The client then fires nudges locally as triggers hit, with no round-trip to backend at trigger time.

That model works fine for static or slowly-drifting nudges. It breaks for filter and sort suggestions on search results. The nudge we want to fire depends on what the user is currently looking at — the sscat they landed on, the filters already applied (via Vaani or the manual drawer), the sort in effect, and the values they have explicitly removed earlier in the session. None of that is known at app open. A pre-cached payload will point users at filters that no longer make sense for the results in front of them.

This KRD ships the runtime content-fetch path for filter/sort nudges: the delay trigger stays client-side; at trigger fire, the client calls the backend with the current search context, and the backend returns freshly-generated nudge content [placeholder based]. All other nudges continue to use the pre-cached content path. This is a targeted extension of the existing infra, not a replacement.

2. Product Thinking

Three claims this KRD wants to support or reject:

  • Runtime content beats pre-cached content for context-dependent nudges. Filter suggestions generated against the live search state should convert (accept rate) meaningfully higher than a pre-cached suggestion generated from stale context.

  • Skip logic prevents the "Vaani ignores my clicks" failure mode. A nudge that re-suggests a value already in active_filters, or a value the user explicitly removed, will burn trust fast. The runtime fetch must honour both sets before selecting content.

2. Scope

2.1 In Scope

  • New backend endpoint: nudge_content_resolve — accepts search context, returns a nudge content payload (filter/sort suggestion + copy + accept/dismiss actions). See 3.2 and 4.2.

  • Client behaviour change: for the filter-nudge trigger rule_id only, content is fetched at trigger fire (post-delay) instead of read from the pre-cached rule payload. All other rule_ids continue to read pre-cached content.

  • Delay trigger: reuses the existing delay-based trigger infra. Delay parameter (default: 5s post-search-result-render) shipped as a tunable rule parameter, not hard-coded. See 3.1.

  • Search context payload from client to backend (sscat, active_filters, active_sort, user_removed, screen, session_id). See 4.3.

  • Skip logic backend-side: any filter value already in active_filters or user_removed is skipped; the ranker walks to the next unapplied, non-rejected value.

  • Freshness SLO: fetch → render within a bounded window; on timeout, the nudge is silently skipped (no stale fallback). See 3.3.

  • Fatigue policy: hard cap on filter nudges per session; back-off after a dismiss. See 3.4.

  • Instrumentation for every trigger fire, every fetch attempt (success, timeout, empty), every render, every user action (accept/dismiss/timeout). See 7.

2.2 Out of Scope

  • The filter application, sscat resolution, state contract, and query stripping — shipped in the parent KRD (Vaani Filter & Sort Application in Search v1).

  • Migrating other nudge rule_ids to the runtime-content path — v1 is scoped to filter/sort nudges only. Broad migration is a fast-follow contingent on latency/reliability observed here.

  • Content personalization beyond the ranker output (e.g., per-user copy variation, LLM-generated microcopy). v1 uses the ranker’s top pick + a templated string.

  • Rich-media nudges (images, carousels).

  • Cross-session fatigue state. v1 fatigue is per-session (app-open).

  • Nudge triggers on screens other than search results. v1 fires on search-result screens only.

3. Product Decision Framework

3.1 Trigger Definition

  • Trigger surface: search-result screen render (Vaani-initiated OR user-initiated search — both are the same client-side event once the results feed is drawn).

  • Trigger type: existing delay-based trigger from nudge infra. Client starts the timer on search-result render.

  • Default delay: 5 seconds. Rule parameter, tunable without a client release.

  • Trigger cancellation: if the user leaves the search-result screen (scrolls to PDP, closes the app, initiates a new search) before the delay expires, the trigger is cancelled and no fetch fires.

Trigger vs content — what changesThe delay-based trigger itself is unchanged. It fires the same way it does for every other delay-based rule shipped at app-open. What changes is only the content-resolution step: for this one rule_id, at trigger fire the client makes a network call to nudge_content_resolve before rendering, instead of reading the payload from local cache.

3.2 Runtime Content Fetch — End-to-End Flow

Sequence, per trigger fire:

  • T0: User lands on search-result screen (Vaani-driven or self-driven). Client starts delay timer for the filter-nudge rule.

  • T0 + delay (default 5s): Timer fires. Client checks that the user is still on the same search-result screen; if not, cancel.

  • T0 + delay: Client assembles the search context payload from local state (sscat, active_filters, active_sort, user_removed, screen, session_id) and calls POST /vaani/nudge_content_resolve.

  • Backend: reads the payload, checks suppress_filters calls the filter_recommendation_ranker with the current context, applies skip logic (skip any value in active_filters or user_removed), walks to the top non-skipped recommendation.

  • Backend: templates the nudge copy against the picked recommendation (e.g., "Sirf cotton dikhaun?"), returns the content payload (see 4.2).

  • Client: on payload receipt within the freshness SLO, renders the nudge. On timeout or empty payload, silently skips (no rendering).

3.3 Freshness SLO & Sort-Turn Handling

  • The nudge content must be fresh with respect to the state at trigger fire. Concretely: the state used to generate content must equal the state the client sent, which must equal the state the user sees.

  • State-drift check: if between trigger fire and payload receipt the user’s state has changed (they applied a filter manually, switched sscat, dismissed the drawer), the client discards the returned payload rather than rendering stale content. This is a client-side check against the state_snapshot_id in the response (see 4.2).

Design decision — no stale fallbackWe chose "silently skip on timeout" over "render the pre-cached fallback" for v1 because a filter suggestion that doesn’t match the user’s current state is worse than no suggestion at all. Cost: some fraction of trigger fires produce no nudge. Benefit: no wrong-context nudges reach the user.

3.4 Fatigue & Back-off

  • Hard cap: 3 filter nudges per session (app-open). After the third, no further filter nudges fire regardless of trigger.

  • Post-dismiss back-off: after a dismiss, no filter nudge fires for the next 60 seconds within the same session.

  • Post-accept behaviour: after an accept, the filter is applied and the trigger re-arms on the next search-result render (the accepted filter shows up in active_filters, so the ranker skips it for the next suggestion).

  • Cross-nudge fatigue: this fatigue counter is scoped to filter/sort nudges. It does not interact with other nudge rule_ids running through the pre-cached path.

3.5 Skip Logic — What the Backend Must Never Suggest

  • Any attribute-value pair already in active_filters for the current sscat.

  • Any attribute-value pair in user_removed for the current sscat (user explicitly rejected it earlier in the session).

  • When suppress_filters is true, the backend returns an empty payload immediately without calling the ranker.

  • If the ranker’s full ranked list is exhausted by skip logic, the backend returns an empty payload. The client silently skips.

3.6 Nudge Content — Copy Templates (v1)

  • Add-filter template: "Sirf {value} {sscat} dikhaun?" — e.g., "Sirf cotton kurti dikhaun?"

  • Price-range template: "{value} tak filter karun?" — e.g., "500 tak filter karun?"

  • Sort follow-up template: "Sirf top-rated dikhaun?" (fires after sasta if rating filter hasn’t been suggested yet, and vice-versa — governed by ranker output, not by response LLM).

  • All copy is templated on the backend at content-resolve time. Copy variants are owned by PM and can be updated without a client release.

  • Actions: single accept button ("Haan, dikhao") + dismiss (×). No free-form input on the nudge itself.

3.7 Interaction with the Vaani Response LLM

  • The Vaani response LLM does NOT generate filter suggestions. This is a hard rule inherited from the parent KRD.

  • The only clarifier the response LLM may emit is the sort clarifier (after sasta or achhi quality), asking for a specific budget / rating threshold. See parent KRD section 3.7.

  • Everything else — next-best filter, refinement prompts, upsell of a related attribute — goes through this runtime nudge path.

Summary

V1 extends the existing delay-based nudge infrastructure with a runtime content-fetch path for filter/sort nudges. Required build:

  • New backend endpoint nudge_content_resolve — accepts search context, returns nudge content at trigger time.

  • Client behaviour change scoped to the filter-nudge rule_id: content fetched at trigger fire, not read from pre-cached rule payload. All other nudges unchanged.

  • Freshness SLO: P95 ≤ 400ms trigger fire → render. State-drift check via state_snapshot_id; no stale-content fallback.

  • Backend-side skip logic: active_filters, user_removed all honoured before ranker consultation

  • Instrumentation covers every trigger fire, fetch attempt, state-drift event, render, and user action.

Filter application, sscat resolution, state contract, and query stripping ship in the parent KRD. Migration of other nudge rule_ids to the runtime-content path is a fast-follow.
