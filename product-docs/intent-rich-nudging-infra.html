Product Thinking.

Product that we have right now:

  • one trigger type (zero-click product exposure),

  • static config copy,

  • client-only counters,

  • surfaces FY/Search/CLP.

  • No user context in the copy,

  • no prior-session memory,

  • no priority resolver (between nudges)

Two things we want achieve:

  • Drive Vaani adoption in such a way that it really gives users an immediate value

  • Create it in a manner that users understand the unique value proposition of the surface so that they retain it and it becomes a habit.

Meta Approach

  • Proactively engage users.

  • engage users when we have a strong hypothesis that they need help.

  • engage users with more contextually relevant content so that users feels that voice as a surface understands them and is intelligent.

What we want to prove using this:

  • Vaani adoption through above approach creates immediately impact

    • reducing zero click sessions for users.

    • creating conversion goodness in same session.

    • reducing the number of session it takes user to place an order.

  • Vaani adoption through above approach creates increases organic vaani usage.

  • Vaani adoption through above approach makes user stick with the platform organically in the long run

  • Vaani adoption through above approach makes user try Vaani in more exploratory ways for things app (and even Vaani) is not currently equipped with.

What we will build as an MVP:

We will design our experiment for users based on their latest intent based on last few days and what they are doing on the app in the current app version. For this there will be following axis.

AxisValuesWhat this means
A — Intent prior (last N days) - Exploit in sscat S (≥ threshold% clicks on one sscat) - Explore (diffuse, has predicted basket Z) We can classify users as exploit or explore based on whether the percentage of their clicks in any single SSCAT (S) over the last N days exceeds a predefined threshold.For explore users, we will also identify the set of categories (z) that the platform hypothesizes the user is likely to engage with. These candidate categories will be derived from the various candidate generation models available on the platform.
B — Current-session click state - Zero-click - On-intent clicks (in S) - Off-intent clicks (≠S) - Wide multi-sscat clicks We can trigger nudges based on the user's behavior within the current and previous sessions. For example: - If the user has not clicked on any product up to a given point in their journey. - For exploit users, if they have made more than X% of their clicks in a specific SSCAT (S) or have accumulated at least Y clicks in that SSCAT (S) - Based on the diversity of the user's engagement, such as the number of distinct SSCATs they have clicked on so far in their journey.
C — Search state (in current session) - No search - Searched Based on search behavior, allowing different nudges for users who have initiated a search versus those who have not searched yet.
D — Prior-session hook - None - Prev-clicked product not re-shown - Intent carry-over – Cart/payment/wishlist abandonment Based on cross-session engagement patterns. For example, if a user previously clicked on a product in previous session, say in current session after viewing Y products, we can nudge them At app open, based on actions from the previous session, such as users who added an item to their cart, added an item to their wishlist, or abandoned their journey after reaching one of these stages. Each of these behaviors can trigger a different personalized nudge.

A and B are the primary branch. C is mostly a gating condition ("no search done" = intent not yet expressed). D produces override nudges that can outrank the A×B leaf.

New Android Counters:

Meta Change: the big one is sscat-tagged impressions. Every impression/click must carry its sscat so the client can reason per-sscat:

  • *product_views_by_sscat{}* and distinct_product_views_by_sscat{}****

  • *product_clicks_by_sscat{}*

  • *distinct_sscats_viewed_count, distinct_sscats_clicked_count***

  • *Derived from the maps + backend's* exploit_sscat : exploit_sscat_view_count*,* exploit_sscat_distinct_views*,* exploit_sscat_click_count*,* on_intent_click_share (= clicks in S / session clicks)****

  • *session_searched_flag* / session_search_count (gates E3, X1 — "no search done")****

  • *prev_clicked_product_shown_count* + prev_clicked_product_seen_flag (needs backend-pushed product id; counts from app open)****

  • *Nudge state for back-off:* session_nudges_total, lifetime_nudges_total, lifetime_ignored_nudges_total, lifetime_ignored_nudges_perc [we will define lifetime as x days ]****

Android only consumes:

  • the exploit / explore

  • category in which user is exploit

  • whether exploit user is new to category in that category.

  • Category predicted basket for explore users (based on cross category cg)
