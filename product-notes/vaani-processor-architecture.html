Product Note · Data Enrichment

Vaani Processor Architecture

Thinking on the shape processors should take as Vaani goes from one to many: what a processor is, how the intent layer selects them, and the contract their output has to satisfy before it reaches the LLM.

Status  Thinking, for discussion Owner  Ishan Builds on  KRD Vaani V0 Data Enrichment · Two-Layer Architecture Spec v2

01The model

A processor is a named, LLM-addressable unit of information. The intent layer decides which processors a turn needs; the orchestrator runs them in parallel; each one turns a downstream API's JSON into a compact token block the response layer can read.

Today Vaani has one processor — product_info, which calls storefront on PDP turns and emits a single PRODUCT_DATA line into the response prompt. Everything in the V0 Data Enrichment KRD is more of the same shape: more fields, from more downstream systems, at more grains. The point of writing this down now is that product_info works but nothing about its shape is recorded anywhere. If the next several processors each invent their own output format, suppression handling and fetch semantics, we will be unpicking that for a long time.

Four invariants

One processor, one downstream API

A processor never fans out to two systems. If information needs two calls, it is two processors. This keeps latency, failure and ownership attributable to a single named unit.

Suppression happens in the processor

The KRD's silent-when thresholds are enforced in code, before emit. The LLM never sees a number it is not allowed to use, so it cannot leak one.

A processor is never on the critical path

Timeout or error means the block is omitted and the turn continues. A missing block degrades the answer; it never fails it.

Semantics, not endpoints

Processors are named for what they mean to the assistant — "post-order truth about this product" — not for the service behind them. The LLM addresses meaning; plumbing can move.

02A turn, end to end

The processor step sits between the two existing LLM calls. Layer 1 gains one output field; Layer 2's inputs gain one block per resolved processor. Neither layer changes otherwise.

03The processor contract

Every processor — the one that exists and the ones that don't yet — declares exactly these eight things. A processor whose spec has a blank in this table is not ready to build.

DeclarationMeaning
name<entity>_<facet>, snake_case. Entity is one of product, seller, user, context. The name is what Layer 1 emits and what the token block is named after, so it is a public interface — renaming it is a prompt change.
keys requirede.g. product_id + seller_id. If a key is unavailable this turn, the processor is not invocable and the orchestrator drops it silently — no error, no empty block.
downstream APIExactly one. Named service + endpoint. If a processor needs two, it is two processors.
freshnessRT / NRT / BATCH, per KRD §4.4. Determines whether a stale read is acceptable and how aggressively the result can be cached within a session.
latency budgetIn ms. On breach the block is omitted and logged to meta.processors_failed. The KRD guardrail is P95 no worse than +200ms end to end, so budgets must sum within that under parallel execution.
emitted blockThe block name and the exhaustive key list, with units and formatting. This is the contract the response prompts are written against.
silent-whenPer-key suppression rules, from the KRD field catalogue. Enforced here, never in a prompt.
eligible intentsWhich Layer 1 intents may request it, and which get it by default. Drives the resolver in §04.
Non-negotiable

Sanitization is code-level, not prompt-level. KRD V-D5 exposes returner_tier as a tone modulator but requires overall_return_rate and reason_mix to be stripped. That stripping happens inside the processor. A prompt line saying "never mention this" is not a control.

04How processors get selected

Layer 1's output grows one field. It already returns intent, screenshot need and pivot signal; it now also returns the processors it thinks the turn needs.

{
  "intent": "PRODUCT_INQUIRY",
  "requires_screenshot": false,
  "pivot_signal": false,
  "processors": ["product_post_order_info"]
}

The LLM's request is advisory, not authoritative. The orchestrator resolves the real set:

final = default_map[intent] ∪ (llm_requested ∩ allowlist[intent])

The default map is a deterministic floor and the allowlist is a ceiling. The classifier runs on a small, fast model; if it forgets to request product_info on a price question, that is a broken turn, and no amount of prompt tuning takes that failure mode to zero. The floor removes it entirely. The ceiling stops a hallucinated processor name, or an expensive fetch on a GREETING.

This also settles KRD §7 open item 5 — the lazy past-orders fetch — in favour of orchestrator-side triggering, which is what the KRD itself recommends.

05The output contract

This is the part that actually determines answer quality. Downstream APIs return nested JSON built for services, not for language models. The normalizer's job is to throw most of it away and pre-chew the rest.

Grammar

One block per processor. Block name is the processor name, uppercased. Pipe-delimited key=value, one flat line — the same shape product_info already emits today:

PRODUCT_POST_ORDER_INFO: |return_rate_m3=12% (category 22%, better)
|delivered_m3=1284|top_return_reason=size (58% of returns)|quality_returns=4%

(wrapped here for legibility; emitted as one line)

Normalization rules

RuleWhy
Omit, don't null
A suppressed key is absent from the block entirely.		 The KRD emits null and instructs the LLM to ignore it. Omission is strictly stronger — a model cannot surface, hedge about or apologise for a key that was never in its context. It is also cheaper.
Empty is not silence
For list processors emit orders=none when the list is genuinely empty.		 "Aapka koi order raaste mein nahi hai" is a correct, useful answer. Absent means stay quiet; none means a real fact was established. These must be distinguishable — KRD F1/F2 already say return [], not null.
Precompute every framing
return_rate=12% (category 22%, better), not two raw floats.		 Any arithmetic or comparison left to the LLM is a hallucination surface. If the response prompt is going to say "better than most", the word better should be computed upstream.
Pre-resolve dates
eta=Sat 18 Jul (4 din), never an ISO timestamp.		 Date arithmetic is unreliable in LLMs and the output is Hindi anyway. Give the phrase, not the input to a calculation.
Cap every list at the processor
variants ≤ 8, past orders ≤ 10, review themes ≤ 3.		 Bounded prompt size and predictable latency. The cap is config, never part of the processor's name.
One level of nesting, maximum
{k:v,k:v} and [a,b,c]. Deeper structures flatten to dotted keys.		 Today's size_chart={…sizes:[{size:S,dimensions:[36,42]}]} is two levels deep and gets read inconsistently.
No raw IDs
Unless an action genuinely needs one.		 variant_id is pure noise unless Vaani is going to select that variant. Same for order IDs on a turn that only narrates status.
Per-processor size budget
Enforced at emit, in characters.		 Every block rides in the Layer 2 system prompt. Unbounded blocks silently degrade both latency and instruction-following.
A live example of why rule 3 matters

product_info currently emits rating_distribution={4_star:2100,5_star:4200} alongside total_ratings=8842. The PRODUCT_DETAILS prompt then asks the model to say "[X]% लोगों ने 4-5 स्टार दिए हैं." So the LLM is dividing 6300 / 8842 in its head — from a distribution map that is missing its 1-, 2- and 3-star buckets entirely.

Emit pct_4_5_star=71% and both the arithmetic and the partial-map bug disappear. Every existing key in PRODUCT_DATA deserves this audit before new processors copy the pattern.

Emitted to Layer 2

PRODUCT_POST_ORDER_INFO: |return_rate_m3=12% (category 22%, better)|delivered_m3=1284

Roughly 900 characters of JSON become roughly 150 characters of text, and every number in it is already in the form the response prompt wants to speak. The category comparison is made in code rather than by the model; the three windows collapse to the decision-relevant grain plus a derived trend; and per KRD A2, if no reason clears 25% share or the sample is under 50 returns, top_return_reason is omitted entirely rather than reported weakly.

09Adding a processor

The checklist for anyone building the next one.

  1. Fill in all eight contract fields from §03. A blank means it isn't specified yet.
  2. Confirm it maps to exactly one downstream API. If not, split it.
  3. Write the emitted block by hand first — the literal text, with real values. If you can't write the line, the field selection isn't finished.
  4. For every key: what will the response prompt say with it? Anything requiring arithmetic, comparison or date math gets precomputed into the value.
  5. Transcribe the silent-when rules from the KRD field catalogue into code, and confirm suppression means omit the key, not emit null.
  6. Decide empty-vs-absent for every list key, and make them emit differently.
  7. Add the processor to default_map and allowlist for its intents. A processor no intent can request is dead code.
  8. Set the latency budget and confirm the parallel worst case still fits the +200ms P95 guardrail.
  9. Add hit / miss / timeout / suppression-rate logging. Per-key surface rate is a KRD secondary metric and it can only be measured from here.
